## 1. 차별화 핵심 (최우선)

### 1-1. 상황 기반 자가 복구 — 글로벌 인터럽트 워처 **[2차]**

전이 도중 광고·업데이트 팝업이 뜨면 경로가 통째로 무너진다. 워처를 "판정" 용도로만 두지 말고
**가로채기(hijack)** 를 시킨다.

* `StateGraph` 에 **인터럽트 상태** 개념 추가: `State.interrupt = True` 인 상태는 어떤 상황에서든
  감지되면 최우선으로 처리한다(예: `광고팝업`, `업데이트알림`).
* 인터럽트 상태에는 **탈출 전이**를 등록한다(닫기 버튼 클릭 등).
* 엔진 흐름: 워처가 인터럽트 감지 → 현재 진행 중인 전이/노드를 **일시 중단** → 탈출 전이 실행 →
  원래 목표 상태로 경로 재계산 → 중단 지점부터 재개.
* 재진입 안전장치: 같은 인터럽트가 N회 연속 발생하면 실패 처리(무한 팝업 루프 방지).
* 에디터 작업: 상황 관리 창에 "인터럽트 상황" 스위치와 탈출 전이 표시.

### 1-2. 사람처럼 움직이기 **[완료 — 1차 반영]**

`itda/core/humanize.py` 가 궤적·타이핑·클릭 시간을 생성한다. 스위치 UI와 실시간 미리보기가
편집기에 들어가 있다. **2차 입력 주입부는 반드시 이 함수들을 통해서만 좌표/시간을 만든다.**

| 스위치 | 효과 |
|---|---|
| 곡선 궤적 | 3차 베지에. 제어점을 진행 방향의 수직으로 밀어내고 좌우·크기를 무작위화 |
| 가속 · 감속 | ease-in-out. 지수를 궤적마다 다르게 뽑음(단조 증가 유지 — 총 이동 시간 보존) |
| 오버슈트 | 목표를 지나쳤다가 되돌아옴 |
| 미세 정지 | 이동 중 1~2회 40~110ms 멈칫 |
| 타이핑 리듬 | 글자 간격 0.55~1.75배, 7% 확률로 길게 멈춤 |
| 클릭 시간 변화 | 누름 시간 0.6~1.9배 |
| 대기 중 드리프트 | 대기 시 커서 미세 이동 |

액션마다 `humanize = 프로파일 따름 / 이 동작만 켬 / 이 동작만 끔` 으로 개별 제어한다.

### 1-3. 입력 장치 우선순위 뮤텍스 **[2차]**

멀티 플로우가 물리 마우스·키보드를 동시에 만지면 서로를 망친다.

* `InputArbiter` 싱글턴: 우선순위 큐 기반 획득/반납.
* `FlowEntry.priority` 가 큰 쪽이 먼저 획득. 낮은 쪽은 대기하거나(기본) 선점 양보.
* 획득 단위는 **액션 하나가 아니라 노드 하나** — 클릭과 그 뒤의 문자 입력이 다른 플로우에 끼어들려
  쪼개지면 안 된다.
* 데드락 방지: 획득 타임아웃 + 강제 반납, 획득 상태를 실행 상태 패널에 표시.

### 1-4. 단일 실행 파일 배포 **[2차]**

* PyInstaller `--onefile` 기준 스크립트 작성. OpenCV DLL, PyQt6 플러그인(platforms/imageformats)
  누락 여부를 빌드 후 스모크 테스트로 확인.
* Tesseract 는 **번들에 포함하지 않고** 외부 설치 경로를 찾도록 하되, `kor`/`eng` traineddata 만
  선택 다운로드하는 설치 도우미를 둔다(언어팩 전체는 수백 MB).
* 빌드 산출물 검증: 새 VM 에서 실행 → 새 프로젝트 생성 → 캡처 → 데모 재생까지 자동 확인.

## 2. 실행 엔진 정확도

### 2-1. DPI 배율 좌표 파이프라인 **[2차 · 최우선]**

125%/150% 배율에서 캡처 픽셀과 입력 좌표계가 어긋나면 **모든 클릭이 빗나간다.** 엔진의 첫 작업.

* 프로세스를 Per-Monitor DPI Aware 로 선언(`SetProcessDpiAwarenessContext`).
* 캡처: `QScreen.devicePixelRatio()` 를 곱해 물리 픽셀 기준 이미지를 얻는다.
* 좌표 변환 계층 하나만 두고(`vision/coords.py`) 물리↔논리 변환을 전부 통과시킨다.
  액션·객체·상태가 저장하는 좌표는 **물리 픽셀 기준으로 통일**한다.
* 모니터마다 배율이 다른 경우까지 테스트(주 모니터 100% + 보조 150%).

### 2-2. 템플릿 매칭 2단계 + ROI **[2차]**

4K 전체 화면 매칭은 느리다.

1. **ROI 우선**: 최근 찾은 위치 주변(박스 + 여백 40px)을 먼저 본다. 대부분 여기서 끝난다.
2. **피라미드**: 0.5배 축소본으로 후보를 찾고, 후보 주변만 원본 해상도로 정밀 검증.
3. 다중 이미지(any/best/all)는 축소 단계에서 조기 종료(any 는 첫 성공에서 중단).
4. 캐시 무효화 규칙: 상황이 바뀌면 해당 상황에서 얻은 위치 캐시를 버린다.

### 2-3. 워처 스레드와 프레임 버퍼 공유 **[2차]**

* 워처는 `QThread` 에서 돌고 결과만 이벤트 버스로 넘긴다(현재 GUI 계약 그대로).
* 캡처 프레임은 `np.ndarray` 하나를 만들어 워처와 매칭이 **뷰로 공유**한다. 프레임마다 복사하면
  700ms 주기에서도 RAM/CPU 가 눈에 띄게 오른다.
* 프레임 세대 번호를 붙여 "같은 프레임에 대한 중복 매칭"을 건너뛴다.

### 2-4. 캡처·동시성 결함 3건 **[완료]**

외부 리뷰에서 지적받은 세 건. 각각 재현부터 시도했고, 재현 안 된 것은 안 됐다고 그대로 적는다
— 고치는 것 자체는 문서화된 정석과 다를 게 없어서 손해가 없다.

* **GDI 비트맵이 DC에 꽂힌 채 `DeleteObject` 됨** (`gdi_capture.py`). `SelectObject` 로
  넣은 새 비트맵을 지우기 전에 원래 비트맵으로 되돌려 놓지 않았다. 실제로 이 머신
  (Windows 11 x64)에서 `GetGuiResources` 로 재 보니 핸들이 새지는 않았다 — 바로 뒤이은
  `DeleteDC` 가 미뤄진 삭제를 마무리해 버리기 때문(문서화된 동작이 아니라 이 빌드의 구현
  세부사항). 그래도 `SelectObject` 로 되돌린 뒤 지우는 게 문서화된 정석이고, 이 지연-삭제
  뒤처리에 기대는 건 다른 Windows 빌드·드라이버(원격 데스크톱 등)에서 실제로 샌 사례가
  보고된 패턴이라 고쳤다. 곁들여 `restype`/`argtypes` 도 전부 명시했다 — 이것도 이 머신에서는
  핸들 값이 항상 32비트 안에 들어와서(HDC/HBITMAP 은 Windows 가 32비트 호환을 보장하는
  핸들 종류) 실제 절단은 못 봤지만, 문서에 없는 우연에 기대는 셈이라 명시해 뒀다.
* **`InputArbiter` 재진입 판정 TOCTOU** (`arbiter.py`). `_Hold.__enter__` 가 "재진입인가"
  를 잠금 밖에서 먼저 읽고 잠금 안에서 `acquire()` 를 따로 불렀다 — 그 사이에 진짜 보유자가
  놓았다 같은 이름으로 다시 잡히면, 방금 새로 잡은(재진입 아닌) 락을 재진입으로 오판해
  `__exit__` 가 놓지 않는다(락이 영영 안 풀림). 스레드 400회 스트레스로는 재현이 안 됐다
  (GIL 때문에 그 틈이 너무 좁다) — 그래서 문제였던 순서 자체를 결정론적으로 재현해 검증했다.
  `_acquire()` 하나로 판정과 획득을 같은 잠금 구간에 묶어 없앴다.
* **작업 스레드에서 QPixmap/QScreen 호출** (`capture.py`, `executors.py`). "screenshot"
  액션이 `capture.grab_all()`/`grab_rect()`(Qt 전용)를 무조건 불렀다 — 멀티 플로우는
  플로우마다 `threading.Thread` 를 새로 띄우므로(`scheduler.py`), 그 작업 스레드에서 이
  액션을 쓰면 Qt 가 그 자리에서 프로세스를 죽인다(Fatal, 예외로 못 잡음. 실제로 재현해
  터뜨리는 건 위험해서 하지 않았다). `grab_array()`(GDI, 스레드 안전) + `save_bgr()`(cv2)
  로 바꿨다. `grab_array()` 자체도 GDI 가 실패했을 때 GUI 스레드가 아니면 Qt 로 폴백하지
  않고 빈 배열을 돌려주게 막았다 — `capture.on_gui_thread()` 로 확인한다.

### 2-7. 실행 속도 — 측정하고 고친 것 **[완료]**

이 머신(모니터 2대, 가상 데스크톱 3440x2640 = 9.1M 픽셀) 기준 실측.

| | 전 | 후 |
|---|---|---|
| 검색 범위 지정 시 화면 캡처 | 131.6ms (전체) | **8.2ms** (300x200 만) |
| `tesseract_path()` (OCR 호출마다) | 6.34ms | **0ms** |

* **검색 범위를 줘도 늘 전체를 찍고 있었다.** 매처가 잘라 쓰긴 했지만 캡처 비용은 그대로
  다 냈다. 이제 `ExecutionContext.screen_region()` 이 그 사각형만 찍는다. 폴링 루프가
  이걸 반복하므로 차이가 그대로 매크로 속도가 된다.
  **위험 지점은 좌표다** — 조각 기준 결과를 화면 좌표로 되돌리고(`Match.offset`), 기억해 둔
  힌트는 반대로 조각 기준으로 옮긴다. 범위가 (0,0) 에서 시작하면 오프셋이 0 이라 "잘라
  왔는지" 를 오프셋으로 판단할 수 없어 플래그를 따로 돌려준다.
* **`shutil.which` 를 OCR 부를 때마다 하고 있었다.** 한 번만 찾고 기억한다.

**고치지 못한 것 — OCR 본체.** `read()` 한 번이 eng 100~120ms, kor+eng 145~165ms 인데,
전처리는 0.1ms 이고 나머지가 전부 **tesseract 프로세스 기동 + 언어 모델 적재**다. 흔히 쓰는
`OMP_THREAD_LIMIT=1` 과 `--oem 1` 을 재 봤지만 이 머신에서는 차이가 없었다(비용이 인식이
아니라 기동에 있어서다). 실질적으로 줄이려면 프로세스를 띄워 두거나 C API 바인딩
(`tesserocr`)을 써야 하는데, 둘 다 구조·의존성 변경이라 별도 판단이 필요하다.
언어를 좁히는 것(kor+eng → eng)만으로도 30% 가까이 빨라진다 — 숫자만 읽을 때는 이미 그렇게 한다.

### 2-6. 입력 잠금 심장박동 **[완료]**

입력 잠금은 노드 단위로 쥐고, 중재기는 30초(`max_hold_ms`)가 지나면 "멈춘 것" 으로 보고
강제 회수한다. 그런데 **시간만 재면 정상적으로 오래 기다리는 노드와 진짜 멈춘 노드가
구분되지 않는다.** 그래서 노드가 아직 실행 중인데 다른 플로우가 잠금을 가져가고, 그 노드가
이미지를 찾은 뒤 클릭하면 둘이 동시에 입력을 주입했다 — 중재기가 막으려던 바로 그 상황이다.

도달 경로가 평범했다: `이미지 대기` 제한시간 60초(스키마는 600초까지 허용), `이미지 찾기`
재시도 30초 초과, `이미지 찾기` + "못 찾으면 실패 처리" 끔(무한 검색).

* 회수 기준을 "쥐고 있은 시간" → **"살아 있다고 마지막으로 알린 뒤 지난 시간"** 으로 바꿨다
  (`InputArbiter.touch`).
* 심장박동은 `ExecutionContext.check_stop()` 에서 보낸다 — 이미지 찾기·대기의 폴링 루프와
  `ctx.sleep` 이 매 회차 부르는 지점이라, 정상 노드는 자연히 살아 있다고 알리게 된다.
  진짜 멈춘 플로우는 여기 못 오므로 회수는 예정대로 걸린다.
* 이름은 `ctx.flow_key` 가 아니라 러너가 채우는 `ctx.arbiter_owner` 를 쓴다 — 서브플로우를
  부르는 동안 `flow_key` 가 바뀌어서, 정작 잠금을 쥔 바깥 플로우에게 박동이 안 간다.

**테스트가 두 번 틀렸던 것도 남겨 둔다.** ① 처음엔 `arbiter.owner` 만 읽어 검사했는데, 회수는
`acquire()` 안에서만 발동하므로 고치기 전에도 통과했다. ② 고친 뒤엔 박동을 6회로 끊고 도둑은
400ms 를 기다리게 해서, 박동이 멈춘 뒤 회수가 걸려 **고쳐 놓고도 실패**했다. 지금은 도둑의
대기(200ms)가 박동 구간(360ms) 안에 들어가도록 잡는다 — 실행 중인 노드는 잠금을 놓을 때까지
계속 뛰기 때문이다.

### 2-5. 창 선택 도구 **[완료]**

창 맞추기 노드/액션에서 제목·위치·크기를 손으로 재는 대신, 화면에서 창을 직접 골라 채운다.

* `itda/gui/tools/window_picker.py` — 스크린샷 도구와 같은 얼린 화면(`FrozenOverlay`) 위에서,
  마우스 아래의 창을 실시간으로 찾아 붉은 테두리로 감싼다. 창 목록은 도구를 열 때 **한 번만**
  찍어 둔다(z-순서상 첫 번째 일치 = 가장 앞의 창, `WindowController.find()` 와 같은 규칙).
  클릭하면 그 창의 제목과 **눈에 보이는 기준의** 위치·크기(투명 테두리 보정 적용됨,
  §3-4 참고)를 돌려준다.
* 필드 하나가 아니라 제목·일치방식·위치·크기 네 칸을 한꺼번에 채워야 해서, 스키마가 자동
  생성하는 낱개 편집기로는 안 됐다 — `PropertyPanel` 이 "창 선택" 버튼을 창 노드/액션
  섹션에만 직접 끼워 넣고, 네 칸을 `QUndoStack.beginMacro()/endMacro()` 로 묶어 되돌리기
  한 번에 되돌아가게 했다(`scene.py` 의 붙여넣기가 이미 쓰던 방식).
* 일치방식은 항상 "정확히" 로 채운다 — 그대로 가져온 제목 문자열이니 "포함" 보다 안전하다.
* 실제 창으로 검증: 픽커가 열거한 box 가 `WindowController.box_of()` 의 win32 진짜 값과
  정확히 일치. (Qt 의 `setGeometry()` 로 만든 테스트 창은 프레임을 뺀 좌표라 요청값과
  다르게 나오는데, 이는 픽커가 아니라 Qt/Win32 좌표 관례 차이다 — 그래서 검증은 요청값이
  아니라 `WindowController` 의 실측값과 비교했다.)
* **잇다 자신의 창은 프로세스 단위로 뺀다** (`WindowRef.pid` + `current_process_id()`).
  처음엔 오버레이 핸들 하나만 걸렀는데, §3-5 에서 대화상자를 "숨기지 않고 투명하게만" 만들도록
  바꾼 것과 정면으로 부딪혔다 — **투명도 0 인 창도 `EnumWindows` 에는 그대로 잡힌다.**
  그래서 노드 편집 창에서 도구를 열면 안 보이는 그 창이 아래 대상 앱 대신 선택됐다. 하필
  이 기능을 쓰는 주 경로가 정확히 거기였다. 핸들 필터는 애초에 죽은 코드이기도 했다
  (`_enumerate()` 는 `show()` 전에 도므로 오버레이가 아직 `IsWindowVisible` 이 아니다).
* **방향키도 강조를 갱신한다.** `mouseMoveEvent` 에서만 갱신하던 탓에 방향키로 커서를 옮기면
  테두리가 이전 창에 남아 있다가 Enter 로 그대로 확정됐다. `_sync_hover()` 로 묶어 둘 다에서
  부른다.

## 3. 에디터 개선

### 3-1. 계층적 자동 정렬 (Sugiyama) **[2차]**

현재 `auto_layout()` 은 BFS 깊이로만 열을 나눈다. 합류·역방향 간선이 있으면 겹치고 꼬인다.

* 레이어 할당(longest-path) → 역방향 간선 임시 반전 → 더미 노드로 긴 간선 분할 →
  중앙값 정렬(median heuristic)로 교차 최소화 → 좌표 배정.
* 외부 의존성(graphviz) 없이 구현한다(배포 단순성 유지).

### 3-2. 캔버스 성능 **[완료]**

노드 300개로 재어 보고 고쳤다. 추측 대신 측정으로 대상을 골랐다.

| | 개선 전 | 개선 후 |
|---|---|---|
| 줌 (노드 300) | 44.7ms/회 | **27.7ms/회** |
| 줌 (노드 800) | 68.1ms/회 | **35.3ms/회** |
| 팬 (노드 300) | 4.5ms/회 | **0.1ms/회** |

* **포트 숨김이 가장 컸다.** 노드 300개면 포트가 904개다. 부분별로 숨겨 가며 재 보니 줌 비용의
  3분의 1이 포트였다. 배율 0.5 아래에서는 점으로만 보이므로 감춘다 — 상태가 바뀔 때만 손대서
  평소 줌에는 비용이 없다.
* **상세도(LOD) 렌더링** — 축소하면 노드는 요약·배지·출구 라벨을, 엣지는 화살촉·라벨을 생략한다.
  글자 그리기가 가장 비싸다.
* **아이템 캐시는 넣었다가 뺐다.** 줌마다 무효화돼 44.7 → 43.0ms 로 이득이 없었고 메모리만 썼다.
  팬은 뷰의 배경 캐시만으로 충분히 빨라졌다.

### 3-3. 모달 대화상자 위에서 화면 도구 쓰기 **[완료]**

노드 편집 창(모달)에서 좌표 도구를 열면 ① 커서를 따라오지 않고 ② 좌표를 찍으면 편집 창이
닫혀 버렸다. 원인이 둘이었고, 둘 다 Qt 의 기본 동작을 몰라서 밟은 함정이다.

* **오버레이가 모달이 아니었다.** 앱 모달 대화상자가 떠 있으면 다른 창은 이벤트를 못 받는다.
  마우스가 움직여도 `mouseMoveEvent` 가 오지 않고, 클릭은 아래 대화상자로 새어 나간다.
  → 오버레이를 `ApplicationModal` 로 만들어 모달 스택의 꼭대기에 올린다.
* **대화상자는 숨기면 안 된다.** `QDialog` 는 감춰지는 순간 `exec()` 루프를 끝낸다(확인함).
  캡처 전에 창을 치우려고 `hide()` 하면 그게 곧 "편집 창이 닫힘" 이다.
  → 대화상자는 `setWindowOpacity(0)` 로 투명하게만 만든다. 실제 화면에서 재어 보니
  캡처에서 완전히 사라지고(표식 픽셀 78/78 → 0/78) 창은 살아 있다.
* 덤으로 **부모 창을 숨겨도 자식 대화상자는 화면에 남는다**(78/78). 그래서 예전처럼 메인 창만
  숨기는 것으로는 편집 창이 계속 찍혔다.
* 오버레이가 다른 경로(Alt+F4 등)로 닫혀도 대기 루프를 끝내고 입력 잡은 것을 놓는다.
  안 놓으면 마우스를 붙잡은 채 루프가 남아 앱 전체가 멈춘다.

### 3-4. 창 제어 정확도 **[완료]**

"창 제어에 허용오차가 같이 걸린 것 같다" 는 지적에서 시작했다. 재 보니 **허용오차는 걸려
있지 않았고**(극단 프로파일 30회 반복 → 사각형 1가지, 대기 300ms 정확), 원인은 다른 데
두 개 있었다. 창 제어에는 변동계수를 걸지 않는다는 규칙은 코드 주석으로 못을 박았다.

* **보이지 않는 테두리.** Windows 10 부터 창 둘레에 폭 7px 안팎의 투명한 리사이즈 테두리가
  있고 `GetWindowRect`/`SetWindowPos` 는 이것을 포함한 값을 다룬다. 실측:

  | | 값 |
  |---|---|
  | 지정한 값 | (100, 200, 800, 600) |
  | `GetWindowRect` | (100, 200, 800, 600) |
  | **눈에 보이는 창** | **(107, 200, 786, 593)** |

  좌표 도구·이미지 검색이 전부 화면 픽셀 기준이므로 창도 보이는 기준으로 다룬다.
  `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` 로 두께를 재서 넣고 뺀다.
  못 재는 창(구형 창, 최소화 상태)은 보정 없이 지나간다.
* **절대 좌표가 모니터를 못 넘었다.** 화면 밖 방지가 *창이 지금 있는* 모니터를 기준으로
  걸려서, 2번 모니터의 창을 (100, 200) 으로 옮기라고 하면 2번 모니터 구석으로 밀렸다.
  실측에서 (100,200) 요청이 (760,1440) 으로 나와 발견했다. 절대 좌표를 준 경우에는 **그
  좌표가 있는 모니터**를 기준으로 삼는다. 배치(프리셋)는 지금 있는 화면 기준이 맞으므로 그대로.
* **적용 결과를 확인한다.** 최소 크기가 정해진 창이나 스냅이 걸린 창은 조용히 다른 크기가
  되는데 그러면 이후 좌표가 전부 어긋난다. 적용 후 다시 읽어 다르면 경고 로그를 남긴다.

확인(실제 창): 위치·크기 지정 / 반복 / 작은 크기 / 왼쪽 절반 / 화면 가운데 전부 요청값과
보이는 창이 일치.

### 3-5. 실행 중 편집 잠금 **[완료]**

실행은 GUI 스레드에서 돌면서, 정지 버튼과 F12 가 살아 있도록 정지 확인 시점마다
`processEvents()` 를 부른다(`RunController._tick`). 응답성을 위해 필요한 구조지만, **그 틈에
사용자가 편집하면 엔진이 들고 있던 모델과 화면이 어긋난다** — 노드 삭제, 탭 닫기, 프로젝트
새로 열기, 되돌리기가 전부 실행 도중에 끼어들 수 있었다.

실행하는 동안 편집기를 읽기 전용으로 만든다.

* 캔버스는 **비활성화하지 않는다.** 실행 상황을 봐야 하므로 선택·드래그·드롭·오른쪽 클릭
  메뉴의 편집 항목만 막고, 줌·팬은 남긴다(`FlowView.set_read_only`).
* 편집 패널(프로젝트·팔레트·객체·노드 액션·속성)은 잠그고, **로그·실행 상태 패널은 살려 둔다.**
* 탭 닫기를 막는다 — 탭을 닫으면 씬이 통째로 사라진다.
* **모달 대화상자를 여는 동작을 전부 잠근다.** 실행이 `processEvents` 안에서 도는 구조라,
  그 위에 대화상자가 이벤트 루프를 하나 더 얹으면 닫을 때까지 매크로가 멈춘다.
  타이밍·상황 관리·객체화 도구는 물론 "잇다 정보" 까지 포함된다.
* 실행 중 창 닫기는 정지 신호만 보내고 무시한다. 그대로 닫으면 엔진이 아직 쓰고 있는 씬이
  사라진다.
* 정지(F12·정지 버튼)는 당연히 잠그지 않는다.

### 3-8. 화면으로 확인한 UI 결함 **[완료]**

코드만 읽지 말고 **띄워서 캡처해 보자** 는 원칙으로 찾은 것들.

* **출구 라벨이 겹쳐 찍혔다.** 기본 노드 높이(62px)에 출구 2개를 넣으면 간격이 8px 인데,
  7pt 라벨의 글자 높이가 9px 이라 "성공"·"실패" 가 서로 위에 찍혔다. 높이 계산이 출구
  개수를 전혀 보지 않았다 — `PORT_SPACING(17px) * (출구+1)` 만큼은 확보하도록 고쳤다.
  출구가 하나면 겹칠 일이 없으므로 예전 높이를 유지한다.
* **기본 창에서 도구모음이 넘쳤다.** 필요폭 1501px > 기본 창 1500px 라 "검사" 가 이미 넘침
  메뉴에 숨어 있었다. `검사` 를 아이콘만으로 돌리고 "멀티 플로우 실행" → "멀티 실행" 로
  줄여 1425px 로 맞췄다.

**남은 것(설계 판단 필요)**: 창을 1100px 아래로 줄이면 **실행 정지**가 넘침 메뉴로 숨는다.
Qt 도구모음은 넘칠 때 뒤쪽부터 감추는데 하필 뒤쪽에 실행 제어가 있다. F12 전역 단축키와
상태바 안내가 있어 치명적이진 않지만, 실행 제어를 도구모음 앞쪽으로 옮기거나 상태바에 정지
버튼을 두는 편이 낫다 — 배치가 바뀌는 일이라 임의로 손대지 않았다.

### 3-7. 캔버스 화면 이동(패닝) **[완료]**

가운데 버튼 드래그, Alt/Shift + 좌드래그로 화면을 옮긴다. 플로우 캔버스와 액션 시퀀스 뷰가
같은 조작이어야 해서 `itda/gui/canvas/panning.py` 의 `PanMixin` 한 곳에 두었다 — 처음엔 두
뷰에 같은 코드가 그대로 복사돼 있어서, 한쪽만 고치고 다른 쪽을 잊기 딱 좋았다.

* **Shift 를 써도 되는지 먼저 확인했다.** Qt 의 다중 선택 수식키는 `Ctrl` 이고, `Shift` 는
  이 씬에서 원래도 아무 일도 하지 않았다(넣기 전후 모두 클릭 하나에 하나만 선택 — 되돌려서
  비교함). 그래서 가로채도 잃는 기능이 없다.
* 수식키 없는 좌드래그는 그대로 고무줄 선택이다.
* **읽기 전용(실행 중)에도 이동은 살아 있다.** `setInteractive(False)` 는 씬으로 가는
  이벤트만 막고 뷰 자신의 핸들러는 그대로 돌기 때문에, §3-5 의 편집 잠금과 자연히 맞물린다.
* 이름이 `alt_or_space_pan`, 주석이 "Alt/Space+드래그" 였는데 **Space 는 어디에도 없었다**
  (실제로는 Alt/Shift). 이름과 주석을 코드에 맞췄다.

테스트에서 한 번 헛짚었다: 이벤트를 뷰로 보냈더니 아무 일도 안 일어나 **전부 통과**했다.
`QAbstractScrollArea` 구조상 `viewport()` 로 보내야 핸들러에 닿는다 — 주석으로 못 박아 뒀다.

### 3-6. 일치 임계값 슬라이더 **[완료]**

이미지 찾기·"객체가 보임" 조건의 `threshold` 파라미터가 숫자 스핀박스라 "0" 이 곧 "상속"
이라는 뜻을 담기 어려웠다. 새 필드 타입 `match_threshold` 를 추가했다
(`itda/core/schema.py`).

* `MatchThresholdEditor` — 체크박스 "기본값 사용 (88%)" + 슬라이더. 체크돼 있으면 슬라이더를
  잠그고 0(상속)을 저장하고, 풀면 슬라이더가 가리키는 값(1~100%)을 저장한다. 두 값의 뜻이
  섞이지 않도록 **저장값(0=상속)과 화면상의 "체크/슬라이더"를 분리**했다.
* 슬라이더 양 끝을 숫자 대신 "불일치 허용 ↔ 정확히 일치" 로 읽어, 이 값이 화면과 등록 이미지가
  얼마나 닮아야 '찾음' 으로 볼지의 기준이라는 걸 바로 알 수 있게 했다.
* 체크를 껐다 다시 켜도 이전에 고른 값을 잊지 않는다(`_custom_pct` 로 따로 기억).
* 잠긴 슬라이더는 손대도 값에 영향을 주면 안 된다 — `checkbox.isChecked()` 일 때는
  `valueChanged` 가 와도 `_emit()` 하지 않는다.
* 잠긴 슬라이더는 시각적으로도 구분되게 `QSlider:disabled` 스타일(회색 손잡이·어두운 트랙)을
  추가했다 — 전에는 잠겨 있어도 코럴색 그대로라 눈으로 구분이 안 됐다.
* `image_search` 액션과 `object_visible` 조건, 둘 다 같은 편집기를 쓴다(선언은
  `itda/actions/vision_actions.py`, `itda/core/conditions.py`).
* 체크박스에 적는 퍼센트는 **프로파일에서 읽는다**(`FormContext.match_default`). 처음엔 88 을
  코드에 박아 뒀는데, 타이밍 대화상자와 객체 패널 **둘 다** 이 값을 바꿀 수 있어서 프로파일을
  0.95 로 올려도 라벨만 "88%" 라고 거짓말을 했다. 객체별 임계값이 우선한다는 사실은 툴팁으로
  알린다(편집기는 어느 객체를 가리키는지 모르므로 그것까지 반영할 수는 없다).

### 완료분 메모

**좌표계 규칙** — 프로젝트에 저장되는 좌표는 **전부 물리 픽셀**이다. 캡처도, 입력 주입도 물리
픽셀로 한다. Qt 위젯을 다룰 때만 논리 좌표를 쓰고 경계에서 변환한다(`to_physical` /
`to_logical`). 배율이 다른 모니터가 섞인 경우까지 테스트로 고정해 두었다.
DPI Awareness 선언은 **QApplication 생성 전에** 해야 하므로 `app.main()` 첫 줄에 있다.

**입력 계층 구조** — `plan_*`(순수 함수) → `Step` 목록 → `Sender`(주입).
이 분리 덕분에 "어떤 좌표를 어떤 속도로 찍을지"를 마우스를 움직이지 않고 검증할 수 있고,
데모 재생(F5)이 같은 계획을 만들어 로그에 보여 준다. 실행 엔진은 `DryRunSender` 를
`Win32Sender` 로 바꿔 끼우기만 하면 된다.

**매칭 3단 축소** — ①최근 위치 주변(힌트) → ②0.5배 축소본에서 후보 → ③후보 주변만 원본으로
정밀 검증. 1920×1080 기준으로 힌트가 맞으면 전체 대비 **5% 미만**, 힌트가 없어도 피라미드로
**절반 미만**의 픽셀만 훑는다(테스트로 고정). `MatchCache` 는 상황이 바뀌면 스스로 비운다.

> 매칭 성질 하나: `TM_CCOEFF_NORMED` 는 밝기·대비 변화에 둔감하다. 테마가 어두워져도 같은
> 버튼으로 인식되는 장점이 있지만, **색만 다른 버튼은 구분하지 못한다.** 그런 경우는 픽셀 색
> 확인이나 OCR 을 함께 써야 한다(테스트에 명시해 두었다).

**창 제어** — 창 크기가 매번 다르면 안의 버튼 좌표도 달라져 매크로가 깨진다. 그래서 창을
정해진 자리·크기로 맞추는 기능을 **노드(`창 맞추기`)와 액션(`창 제어`)** 양쪽에 넣었다.
파라미터 스키마는 `core/window_spec.py` 에 한 번만 정의해 둘이 공유한다. 위치·크기 계산은
순수 함수(프리셋 9종, 모니터 선택, 화면 밖 방지)이고, 실제 `SetWindowPos` 호출만
`engine/window.py` 에 있다.

**실행 엔진** — `Engine` → `FlowRunner` → 액션 `executor`. 편집기에서 정한 규칙(선/후 딜레이,
재시도, 예외 정책, 분기·반복·서브플로우)이 여기서 실제로 동작한다. 이벤트는 데모 재생과 같은
버스로 나가므로 캔버스 하이라이트·로그·변수 워치가 그대로 켜진다.

* **기본 주입기는 `DryRunSender`** — 실제로 움직이려면 `Win32Sender` 를 명시적으로 넣어야 한다.
  GUI 의 `F9 실제 실행` 만 그 경로를 쓴다.
* **비상 정지 `F12`** — `RegisterHotKey` 전역 등록. 잇다 창이 뒤에 있어도 멈춘다. 매크로가
  마우스를 잡고 있으면 정지 버튼을 누르지 못하므로 이게 실질적인 안전장치다.
* 실행은 메인 스레드에서 돌고, `ctx.check_stop()` 마다 이벤트를 처리해 UI 가 살아 있다
  (화면 캡처가 GUI 스레드를 요구하기 때문). 워처를 붙일 때 GDI 캡처로 바꾸면 스레드로 옮길 수 있다.

**상황 머신** — 조건 트리 평가 → 상황 판정 → 최소 비용 경로로 이동. 노드의 `required_state`
는 실행 직전에 강제되고(`navigate`/`wait`/`skip`/`fail`), `state_gate` 노드와
`상황으로 이동`/`상황 대기` 액션이 같은 기능을 쓴다.

* **자가 복구(가로채기)** — `State.interrupt` 를 켠 상황(광고·업데이트 팝업)은 언제 나타나든
  최우선으로 감지된다. 노드를 실행하기 전과 전이 도중에 확인해서, 뜨면 **탈출 전이로 닫고
  경로를 다시 계산해 원래 목표로 돌아간다.** 같은 팝업이 3번 연속 뜨면 포기한다(무한 루프 방어).
* 조건이 하나도 없는 AND 묶음은 **거짓**이다. 참으로 두면 모든 화면이 그 상황으로 판정된다.
* 판정 결과는 250ms 동안 재사용하고, 전이를 실행하면 즉시 버린다(화면이 바뀌었으므로).
* 편집기에서는 상황 관리 창의 **'끼어드는 화면' 스위치**로 켠다. 목록에는 ⚡ 로 표시된다.

**멀티 플로우** — 플로우마다 스레드 하나와 자기 엔진을 갖는다. 변수와 상황 판정은 독립이고
**입력 장치만 공유**한다.

* `InputArbiter` 가 **노드 단위**로 권한을 빌려 준다. 액션 단위로 쪼개면 "클릭 → 문자 입력"
  사이에 다른 플로우가 끼어들어 엉뚱한 창에 글자가 들어간다.
* 우선순위가 높은 쪽이 먼저 가져가고, 같으면 먼저 기다린 쪽이 먼저다(굶지 않게).
* 실행 중인 쪽을 중간에 뺏지 않는다. 대신 **한 플로우가 멈춰 30초 넘게 쥐고 있으면 강제 회수**해
  나머지가 굶지 않게 한다.
* 스레드에서 화면을 찍어야 하므로 캡처를 **GDI(BitBlt)** 경로로 바꿨다
  ([vision/gdi_capture.py](../itda/vision/gdi_capture.py)). Qt 의 `grabWindow` 는 GUI 스레드
  전용이라 멀티 플로우에서 쓸 수 없다. 덤으로 더 빠르다.

**OCR** — Tesseract 5.5(kor/eng)로 확인. 기본 페이지 분할 모드(자동)는 **한글을 세로쓰기로
오해해 글자를 뭉갠다.** 매크로가 읽는 대상은 대개 작은 영역의 한 줄이라 기본값을 `--psm 7`
(한 줄)로 두었고, 액션에서 배치(한 줄/단어/여러 줄/흩어짐/자동)를 고를 수 있다.
그 판단 근거를 테스트로 남겨 두었다(`test_auto_layout_is_worse_for_korean`).

**자동 정렬** — Sugiyama 방식. 역방향 간선 뒤집기 → 레이어 배정 → 더미 노드로 긴 간선 분할 →
중앙값으로 교차 줄이기(4회 왕복) → 좌표 배정. 외부 의존성(graphviz)은 쓰지 않는다.
품질은 `count_crossings()` 로 재고, "예전 깊이 배치보다 교차가 적다"를 테스트로 고정했다.

**배포** — `python tools/build.py` 하나로 아이콘 생성 → PyInstaller → **검증**까지 한다.

* onedir 를 쓴다. onefile 은 실행할 때마다 임시 폴더에 통째로 풀어 시작이 느리다 —
  자주 켜는 매크로 도구에는 맞지 않는다.
* **검증이 핵심이다.** PyInstaller 는 모듈을 빠뜨려도 조용히 성공한다. 그래서 같은 코드의
  콘솔 판(`itda-check.exe`)을 함께 만들고 `--selftest` 로 레지스트리·OpenCV·Qt·프로젝트
  입출력·실행 엔진을 실제로 돌려 본다. 창 프로그램은 stdout 이 없어 출력이 보이지 않는다.
* 쓰지 않는 큰 파일을 스펙에서 걸러 낸다 — ffmpeg(동영상), opengl32sw, Qt6Pdf, Qt6Network 등.
* Tesseract 는 **묶지 않는다.** 언어 데이터까지 넣으면 수백 MB 이고, 설치 여부는 실행 중에
  확인해 안내한다.

**주기 감시** — 설정(`WatcherConfig`)의 주기·미지정 이름·복구 플로우가 실제로 동작한다
([engine/watcher.py](../itda/engine/watcher.py)).

* 감시는 **화면을 읽기만 한다.** 팝업을 닫는 등 입력이 필요한 처리는 실행 엔진이 한다 —
  입력 장치를 쥔 쪽이 처리해야 다른 플로우와 부딪히지 않는다.
* 워처는 **자기 문맥(ExecutionContext)** 을 따로 갖는다. 실행 엔진과 화면 캐시를 공유하면
  스레드끼리 부딪힌다. 주입기도 `DryRunSender` 라 실수로도 입력이 나가지 않는다.
* 상태가 **바뀔 때만** 알린다. 초당 몇 번씩 같은 이름을 흘리면 로그가 쓸모없어진다.
* 모르는 화면이 `unknown_timeout_ms` 넘게 이어지면 복구 플로우를 한 번 부른다(에피소드당 1회).
* 편집기에서도 `F11` 로 켤 수 있다 — 상황 조건이 제대로 걸렸는지 화면을 옮겨 가며 확인한다.

**비동기 플로우** — `플로우 실행`/`플로우 호출` 의 "끝날 때까지 대기" 를 끄면 배경 스레드에서
돌고 곧바로 다음 노드로 넘어간다.

* 자식은 **자기 엔진과 변수 공간**을 갖는다. 부모와 변수를 공유하면 서로 덮어써서 원인을 찾기
  어려운 버그가 난다. 주입기도 따로 준다(기록이 뒤섞이지 않게).
* **입력 중재기만 공유**한다 — 마우스·키보드는 하나뿐이므로 우선순위대로 나눠 쓴다.
* 부모를 정지하면 자식에게도 전달된다. 실행이 끝나면 배경 플로우가 마칠 때까지 기다린 뒤 정리한다.

**남은 확인** — 터치 주입(`InjectTouchInput`)과 창 이동(`SetWindowPos`)은 실제 장치·창에서
검증이 필요하다. 계산·계획 함수는 전부 테스트로 덮었고, 테스트가 실수로 실제 시스템을 건드리지
않도록 `conftest.py` 가 세 곳(입력 주입·터치·창 제어)의 실행 경로를 막아 둔다.
