## 가장 중요한 규칙: 통과하는 테스트는 아무것도 증명하지 않는다

**모든 테스트는 "고치기 전 코드에서 실패하는지" 를 실제로 확인해야 합니다.**

절차:

1. 테스트를 쓴다 → 통과시킨다.
2. **고친 부분을 되돌린다**(그 줄만 원래대로).
3. 테스트를 다시 돌린다. **실패해야 한다.**
4. 실패를 확인했으면 수정을 복원하고 전체 테스트를 돌린다.

3번에서 통과해 버리면 그 테스트는 **버리거나 다시 쓰십시오.** 시간을 아끼려고 이 단계를
건너뛰지 마세요 — 이 프로젝트에서 실제로 세 번, 통과하는데 아무것도 검증하지 못하는
테스트가 나왔습니다.

되돌리기는 파일을 통째로 복사해 두고 특정 줄만 바꾼 뒤 복원하는 식으로 하면 안전합니다.

## 두 번째 규칙: 추측하지 말고 측정한다

"아마 이게 느릴 것이다", "이게 원인일 것이다" 로 고치지 마세요. **숫자를 먼저 뽑으십시오.**

* 성능이면 `time.perf_counter()` 로 전후를 재고 표로 적습니다.
* 원인 추정이면 스파이(함수를 감싸 호출을 기록)를 걸어 실제 호출 순서를 봅니다.
* UI 면 **실제로 렌더링해 캡처하고 눈으로 봅니다**(`widget.grab().save(...)`).

측정해 봤더니 예상과 달랐다면, **그 사실을 그대로 보고하십시오.** "효과 없었다" 는 유용한
결과입니다. 실제로 이 프로젝트에서 Tesseract 의 유명한 튜닝 옵션(`OMP_THREAD_LIMIT=1`,
`--oem 1`)을 재 봤더니 이 머신에서는 차이가 없었고, 그걸 모른 채 적용했다면 "최적화했다" 고
착각했을 것입니다.

## 안전 규칙 — 절대 어기지 마세요

* **실제 마우스·키보드 입력을 내보내지 마세요.** 테스트는 `DryRunSender` 만 씁니다.
  `tests/conftest.py` 가 `Win32Sender.apply`, `TouchInjector.flush`,
  `WindowController.apply` 를 막아 두었습니다. 이 안전장치를 끄지 마세요.
* 실주입 코드(구조체 조립 등)를 시험해야 하면 **시스템콜만 가짜로** 바꾸십시오
  (`SendInput` 을 monkeypatch). 예시는 `tests/test_win32_sender.py` 에 있습니다.
* 사용자의 실제 창을 옮기거나 파일을 지우지 마세요. 임시 폴더를 쓰십시오.

## 이 프로젝트에서 실제로 밟은 함정들 (같은 실수 반복 금지)

### Qt

* **마우스 이벤트는 `view` 가 아니라 `view.viewport()` 로 보내야 합니다.**
  `QAbstractScrollArea` 구조 때문입니다. 뷰로 보내면 핸들러에 도달하지 않아 **테스트가 전부
  통과해 버립니다**(아무 일도 안 일어났으므로).
* **위젯 크기를 재는 테스트는 `style.apply_theme(qapp)` 을 먼저 불러야 합니다.**
  테마 없이 재면 실제 앱보다 버튼이 좁게 나와, 도구모음이 넘치는 상태에서도 통과합니다.
  배치가 실제로 계산될 시간도 줘야 합니다(`QEventLoop` + `QTimer.singleShot(250, ...)`).
* **`QDialog.exec` 같은 sip 메서드를 monkeypatch 하고 원래 값을 되돌려 놓으면 안 됩니다.**
  저장했다 다시 대입하면 원래 슬롯이 아니라 타입에 묶인 래퍼가 들어가, 그 뒤 모든
  테스트에서 `dialog.exec()` 가 `TypeError` 로 깨집니다. 파이썬 하위 클래스에 얹었다가
  `del` 하십시오.
* **`QDialog` 는 감추는 순간 `exec()` 루프가 끝납니다.** 화면 캡처 전에 창을 치우려고
  `hide()` 하면 그게 곧 "대화상자가 닫힘" 입니다. `setWindowOpacity(0)` 을 쓰세요.
* `QRect` 는 경계를 포함합니다 — 50~150 은 101px 입니다.

### 동시성

* **`arbiter.owner` 만 읽는 것으로는 강제 회수가 발동하지 않습니다.** 회수는 `acquire()`
  안에서만 검사되므로, 경쟁 스레드가 실제로 기다리는 상황을 만들어야 의미가 있습니다.
* **경쟁 상황 테스트는 타이밍이 곧 시험 조건입니다.** "살아 있다고 알리는 동안 뺏기지
  않는다" 를 검증하려면, 알림이 **경쟁자가 기다리는 내내** 이어져야 합니다. 중간에 끊으면
  고쳐 놓고도 실패합니다.
* CPython 의 GIL 때문에 좁은 경합 구간은 스레드 스트레스로 재현되지 않을 수 있습니다
  (400회 돌려도 안 나옴). 그럴 때는 **문제였던 호출 순서를 그대로 재현해 결정론적으로**
  검증하십시오.

### 이미지 / OCR

* **단색 이미지는 템플릿 매칭 시험에 쓸 수 없습니다.** 정규화 상관계수(`TM_CCOEFF_NORMED`)
  는 분산이 0 이면 정의되지 않아 아무 데나 맞았다고 나옵니다. 반드시 질감 있는(랜덤) 패턴을
  쓰세요.
* 좌표를 다루는 최적화는 **경계 경우를 꼭 넣으십시오** — 특히 ROI 원점이 `(0, 0)` 인 경우.
  오프셋이 0 이라 "잘라 왔는지" 를 오프셋만으로 판별할 수 없습니다.

### 도구

* **`pip install --dry-run` 은 휠 유무를 알려 주지 않습니다.** 소스 배포판도 "설치 가능" 으로
  보고하고, 실제 설치는 빌드에서 실패합니다. `--only-binary=:all:` 를 함께 주십시오.

## 테스트 스타일

* **이름은 검증하는 사실을 문장으로** 적습니다.
  좋음: `test_drag_walks_to_the_start_instead_of_teleporting`
  나쁨: `test_drag_2`
* **왜 이 테스트가 존재하는지**를 독스트링에 적습니다. 특히 실제로 겪은 버그라면 증상을
  같이 남기십시오("드래그 첫 동작에서 커서가 1274px 튀었다").
* 시간에 의존하는 단언은 불안정합니다. **메커니즘**을 고정하세요(예: "임계값 아래에서 포트가
  숨는가" 는 되지만 "줌이 30ms 안에 끝나는가" 는 안 됨).
* 한국어 주석·독스트링을 쓰십시오. 기존 파일들의 어조를 따라가면 됩니다.
* 콘솔이 cp949 라 한글 출력이 깨질 수 있습니다. 결과 확인은 파일에 UTF-8 로 쓰고 읽으십시오.

## 보고 방식

작업을 마치면 다음을 명확히 구분해 보고하십시오.

1. **무엇을 고쳤고, 되돌렸을 때 어떤 테스트가 어떻게 실패했는지** (실제 실패 메시지 포함)
2. **측정한 숫자** (전/후 표)
3. **재현되지 않은 것** — 고치긴 했지만 이 환경에서 증상이 안 나왔다면 그렇게 적으십시오
4. **하지 않은 것과 그 이유** — 범위 밖이거나 판단이 필요한 것

전체 테스트 수(`python -m pytest tests` 의 통과 개수)를 마지막에 적으십시오.
